# Instructions for working on this repo

Living document — when a new rule is discussed and agreed with the user, add
it here in the same session, not as a follow-up. Don't remove a rule just
because it seems obvious in hindsight; remove it only when the user
explicitly supersedes it.

## Planning documents: where things get logged

Three files, one job each:

- **`planning/ROADMAP.md`** — index of real, scoped features/scope changes,
  one line per milestone, identifier **MMSIM-x** (Mad Mice Shopkeeper Incremental Milestone), in
  commit order. Full detail for each milestone lives in its own
  `planning/features/MMSIM-x.md` file. Write the
  `planning/features/MMSIM-x.md` entry (and its `planning/ROADMAP.md`
  index line) as part of finishing the milestone, not as a follow-up task.
- **`planning/CHANGELOG.md`** — index of bug fixes discovered *after* the
  milestone that introduced them has already shipped, identifier
  **MMSIB-y** (Mad Mice Shopkeeper Incremental Bug), one line per bug. Full detail lives
  in its own `planning/bugs/MMSIB-y.md` file. A bug found and fixed
  while a milestone is still actively being built stays inside that
  milestone's own `planning/features/MMSIM-x.md` entry instead —
  MMSIB is only for things that slipped through and surfaced later.
- **`planning/BACKLOG.md`** — ideas worth keeping that haven't been scoped into
  actual work yet. Once one is picked up, it graduates to
  `planning/ROADMAP.md` with a real MMSIM-x id and is removed from here.

Commit message pattern: `feat: MMSIM-x <milestone name>` for milestone
work, `fix: MMSIB-y <what was fixed>` for changelog work,
`fix: MMSIM-x <what was fixed>` for a same-session fix to a milestone
that's still fresh (not yet promoted to its own MMSIB entry — see the
CHANGELOG.md rule above), `chore: <what changed>` for anything else (docs
restructuring, tooling, cleanup).

**The subject line is the entire message.** No body, no bullet list, no
rationale paragraph, and no trailers of any kind (`Co-Authored-By`, etc.) —
save all of that for conversation or a PR description.
`feat: MMSIM-3 Example milestone` is a complete, correct commit message
on its own.

Several commits made against the same milestone while testing/fixing
mid-development are fine, and normally left for the user to squash
themselves — don't `git commit --amend` or rebase unprompted. But **on
explicit user request**, squash a milestone's `feat:`/`fix:` sequence from the
same session down to one `feat: MMSIM-x` commit for that milestone.

## Commits and pushes

- **Commits are pre-authorized** for this repo specifically: `feat:
  MMSIM-x` / `fix: MMSIB-y` / `fix: MMSIM-x` commits that
  follow the message pattern above and correspond to a real
  `planning/ROADMAP.md`/`planning/CHANGELOG.md` entry, and `chore:` commits
  for docs/tooling/cleanup changes (including edits to this file). This is a
  deliberate exception to the general rule of always asking before
  committing.
- **Never `git push` without asking first, every time** — this is not relaxed
  by any commit pre-authorization above.

## Versioning

Version format: **npm** (`package.json` semver), baseline **0.0.1**.

- **Not bumped automatically per commit.** Bumping is on-demand: invoke the
  **`update-version`** skill (`.claude/skills/update-version/`) when the user
  asks, or naturally once at the end of a session with real changes.
- Bump by the highest-precedence change type since the last
  `chore: bump version to …` commit: any `feat:` → **minor** (patch resets to
  `0`); otherwise any `fix:`/`chore:` → **patch**. Nothing since the last bump
  → nothing to do. **Major** is never auto-detected — only on the user's
  explicit request (resets minor and patch to `0`).
- The bump itself is its own `chore: bump version to …` commit, covered by the
  same commit pre-authorization as any other `chore:` commit.
- Applies going forward from the baseline — past commits aren't retroactively
  versioned.

## Folder structure

- `src/engine/` — pure TypeScript game logic, **no UI/DOM imports**; `step()` is a pure reducer over a seeded, serializable `State`; day cycle is an explicit state machine.
- `src/sim/` — headless bot + `simulate()` for balance (`npm run sim`).
- `src/content/` — zod schema (`schema.ts`) and loader/validator (`load.ts`); `virtual:content` is generated by `scripts/contentPlugin.ts`.
- `src/i18n/`, `src/ui/` — string lookup and Svelte components.
- `content/core/` — data rows (`<table>.json`) and `strings/en.json` + `strings/fr.json`; `content/packs/<name>/` — optional packs (same layout), included only in full builds.
- `public/art/` — placeholder images at their final slot sizes (declared in `artSlots.json`).
- `scripts/` — build-time tooling (content plugin, content check, later the balance simulator).
- Rule: anything that can grow (candies, qualities, stations, customers, shops, tree nodes, errands, text, art slots) is a content row, never a code branch; if a new thing needs engine code, the structure is wrong. Names/text are `*Key` fields, never literals. Preview builds (`npm run build:preview`) exclude packs at build time. The repo
root also holds `planning/` (`ROADMAP.md`, `CHANGELOG.md`, `BACKLOG.md`,
`features/MMSIM-x.md`, `bugs/MMSIB-y.md`), `design/` (design
handoffs — read-only reference) and `docs/` (original documentation and
briefs).

## Testing / verification

- Automated tests: `npm test` (Vitest, `*.test.ts` next to the code). Content
  validity and FR/EN string parity: `npm run check:content` (also run by builds).
  Engine tests must not import UI or touch the DOM.
- TODO: how to verify UI changes (Playwright for browser work, `PrintWindow` for
  Windows desktop builds — never focus-stealing screenshots).
- **At most one dev server per service may be running at a time**, and only
  while actively coding/testing. Before starting one, check whether the port
  is already in use and reuse it if so; when done, kill every process you
  started. Never kill one the user started without asking.
