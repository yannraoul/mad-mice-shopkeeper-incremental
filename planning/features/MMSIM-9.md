# MMSIM-9 — Design brief package and screenshot tooling

Motivation: the author wants to run a Claude Design pass over the interface, and asked for screenshots of all screens, a basic understanding of the game elements, the gameplay loop, and a note that parts of the interface may become interactive/animated later (stirring by moving the mouse or a finger, an animated selectable queue of customers, real-time patience). v1 stays a static proof of concept.

- IN:
  - `docs/design-brief/README.md`: the game and its tone, the gameplay loop (day cycle, weekly stages, story events, a minute of play), the elements in short, the four screens with purpose / content / actions / states, what matters most on each screen, constraints (phone + desktop, touch, EN/FR text length, light/dark, accessibility, fixed-size art slots with a size table and wanted extra art), a section on **future interactivity** (what may come and what it means for the design: think in scenes and objects, separate "what it is" from "how it moves", no turn-based assumptions in the look, keep room; the view-layer architecture lets a different front end replace the renderers), what to deliver back, a list of known weak points, a screenshot index, and the URLs to reproduce each state.
  - `docs/design-brief/elements-catalog.md`: every element as tables (ingredients, candies, qualities, stations, customers, workers, forecasts, skill tree by branch, stages, errands, map places, art slots, key numbers), generated from the real content by `npm run catalog` (`scripts/catalog.ts`) so it cannot drift from the data.
  - `docs/design-brief/screens/`: 17 PNGs generated by `npm run screenshots` (`scripts/screenshots.ts`): 9 desktop dark (morning form, craft bench mid-batch, afternoon with the clerk and feed, evening with tree/report/journal/map/errands, settings, brand-new game morning and afternoon, stage-2 rival active, final stage cleared), 3 desktop light, 5 phone. The generator needs no dependency: it starts the installed Edge/Chrome headless, talks to it over the DevTools protocol (Node's built-in WebSocket), replays each scenario through the real UI on a throwaway developer-hook game, and writes full-page PNGs, so the set can be regenerated after any UI change.
  - Developer URL hooks `money` and `completed` (with tests) so the evening screen can show affordable upgrades and the ending state can be reached: `?seed=&unlocks=&stage=&money=&completed=1`.
- OUT: no visual change to the game; no design decisions taken (the brief states constraints, priorities and weak points, not solutions); no animation or interaction work.
- Verified: the generator produced all 17 images; each was checked by eye (desktop and phone evening, afternoon, bench, ending). `npm run check`, `npm test` (146), `npm run check:content` and `npm run build` pass.
- Incident worth keeping: the first screenshot run showed the evening screen with the map and errands panels spilling over the skill tree (desktop) and the whole page cut off on the right (phone). I first suspected the layout and added grid `minmax(0, ...)` rules, which did not help. The real cause was the dev server serving the raw `ImageSlot.svelte` source as its CSS (so images had no `max-width`), after many hot reloads. Restarting the dev server fixed it; with the real stylesheet the original layout rules were already fine at 1200 px and at phone width (measured, old rules vs new), so the CSS edit was reverted. Lesson recorded in `CLAUDE.md` (Applied Learning).
- Open decisions: customers have no picture of their own yet (only the candy they want), which the brief lists as wanted art; screenshots are English only (French text is about 20 to 30 percent longer; regenerate with the language switched if a French set is wanted); the PNGs add about 3 MB to the repository.
