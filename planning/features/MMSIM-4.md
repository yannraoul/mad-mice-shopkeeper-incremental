# MMSIM-4 — Serve screen and clerk (v1 scope M3)

Motivation: `docs/incremental-game-v1-scope.md` M3: serve screen with queue, decisions, and the clerk automation. Layout stays deliberately basic: a Claude Design pass over all screens comes once every screen exists, and real art replaces the placeholders later.

- IN: afternoon screen (`src/ui/Serve.svelte`) next to the shared `Board` (forecast, contracts, stock). One card per customer at the counter: type, wanted candy (image slot), minimum quality, budget, patience; one "Serve <quality> (<price>)" button per stocked quality that satisfies them (disabled when over budget) plus Refuse; "nothing in stock fits" hint; counter fill, today's tally, a warning that customers still waiting leave when you close; a "Latest" feed of the last 6 sales/refusals/walk-outs (events are translated at render time). Engine: new `delegate` action, `workers.json` table (clerk: unlock `clerk`, serves `faithful`), `settings.delegateAfterBatches` (2), state `delegated` + `batchesMade`. A delegated customer type is sold to automatically by the worker whenever they reach the counter (arrival, refill, or when delegation is switched on mid-afternoon), using the cheapest stocked quality that fits their minimum and budget, and only for recipes crafted by hand `delegateAfterBatches` times. Customers the worker cannot serve (no stock, too poor a fit) stay at the counter for the player. A worker sale does not drain other customers' patience (the clerk works in parallel); player actions do. Events `sold/refused/left` now carry `customerType`, `sold` carries `auto`; the day report has `autoServed`; the simulator bot delegates whenever possible and `npm run sim` prints a `clerk` column. Clerk panel in the afternoon: checkbox per delegated type, training progress per recipe ("Trained on X: n / 2 batches made by hand"). Every worker needs an art slot `worker-<id>`.
- OUT: hiring the clerk (it is an unlock id for now: dev URL `?unlocks=clerk`, real purchase in M4), a second worker type, per-recipe delegation, wages, substituting candies, upsell/price tiers (one recipe only), evening screen, balance.
- Decisions to challenge: delegation is per customer type, training per recipe (both gates must hold); the clerk takes the first matching customer in queue order and picks the cheapest fitting quality (so it never upsells); patience is not drained by clerk sales; delegation can only be toggled in the afternoon UI (engine allows any phase).
- Verified: `npm test` 47 passing (7 new engine tests for delegation, training gate, patience, events, plus a simulator test), `npm run check` 0 errors, `npm run check:content` and `npm run build` clean. Played in the browser (FR): queue renders with all four numbers, serving and refusing update tally, stock, feed and drain the waiting customers' patience (Voyageur 5 -> 3, Marchand 3 -> 1), the counter refills from the line; clerk checkbox on with 1/2 batches trained sold nothing, then after the second batch the clerk sold 5 Faithful customers as the shop opened and the feed showed "Le commis a vendu ...". Not verified: a real phone; Fine/Perfect serving buttons by hand (covered by unit tests).
- Open decisions: the delegation toggle probably belongs in the morning too (so the clerk works from the first customer); whether the clerk should ever refuse or keep a minimum margin; how pending (not yet at the counter) customers should be hinted at.
