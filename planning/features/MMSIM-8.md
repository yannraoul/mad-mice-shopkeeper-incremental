# MMSIM-8 — View layer, boundary test and settings page

Motivation: the engine is meant to be wrapped by different interfaces over time (the current form/text/buttons one for engine testing, later a graphic or animated one). The engine side was already clean, but about 940 lines of "what should this screen show" logic lived inside Svelte components, so a new front end would have had to rewrite them. Also, restarting the game needed a seed in the URL.

- IN:
  - **View layer** (`src/view/`): pure functions `buildXView(content, state, t)` for the header, stage bar, board, errands, map strip, serve screen (customer cards, clerk panel, feed), craft workshop, evening (report, journal, skill tree) and settings menu. They return ready-to-render data: resolved text, ids, art slot ids, numbers (percentages, counts) and, for every interactive element, the engine `Action` behind it plus `enabled`/`why` (the "why not" comes from the engine's own refusal by dry-running the action). Hand-crafting (pick a recipe, tap, tap, stir, shape) is a pure reducer, `craftReduce` over a small `CraftUi`, which hands the finished batch to the engine through a callback.
  - **Application session** (`src/app/session.ts`): framework-free `GameSession` holding state, events, the feed of sales/refusals/walk-outs, the last refusal, persistence (injected), `newGame(seed?)`, save export/import and `subscribe`. `src/app/dev.ts` parses the URL hooks. `src/ui/game.svelte.ts` is now a rune mirror of the session.
  - **Translation core** (`src/i18n/core.ts`): `createTranslate(strings, lang)`; the Svelte store only owns the reactive language. `describeFail`, `unlockName`, `rivalErrands` moved from `src/ui/` to `src/view/text.ts`.
  - **Svelte components are thin renderers** (markup and CSS kept): `Craft`, `Serve`, `Evening`, `Board`, `Errands`, `MapStrip`, `StageBar`, `App`.
  - **Boundary test** (`scripts/architecture.test.ts`, rules in `scripts/lib/architecture.ts`): each folder under `src/` may import only the layers before it (`content` -> `engine`/`craft` -> `save` -> `sim` -> `view` -> `app`); no Svelte, DOM, localStorage, `virtual:content` or build-env use outside the listed adapter files; a new folder must be classified. The test also proves the checker catches violations (wrong-way imports, runes, `document`, unknown packages, unclassified files).
  - **Settings page** (header button): language, **New game** with an optional seed (empty = random, digits only, confirmation first), save export/import and the autosave/dev-mode note. The save panel left the evening screen.
  - Tests: 45 new (view builders, craft reducer flow, menu helpers, session/persistence/new game/import-export, translation core, boundary rules) and a **view-layer bot** (`src/view/viewBot.test.ts`) that plays two weeks using only the session, the view models and the craft reducer, with zero refused actions: the proof that the view layer carries everything a non-Svelte UI needs.
- OUT: no change to the engine, crafting rules, content numbers, simulator bots or save format. Not done: a second front end, animation hooks (events are already available per step), keyboard shortcuts.
- Behaviour change worth knowing: the craft "Made N x ..." message now uses the real batch size (including cauldron upgrades) instead of the base capacity; it was slightly wrong after "Bigger cauldrons".
- Verified: `npm run check` 0 errors, `npm test` 145 passing (balance guards unchanged), `npm run check:content`, `npm run build`, `npm run build:preview` (verify says no pack text in the preview). In the browser, a scripted playthrough of the same seed before and after the refactor (morning form, craft bench mid-batch, Fine form, afternoon, clerk toggled, a sale, evening) produced identical page text for every screen, apart from the save panel having moved to Settings. Settings checked by hand on a throwaway game: new game with a seed, the same seed twice gives an identical game page, an invalid seed shows an error and changes nothing, a cancelled confirmation keeps the game, an empty seed gives a fresh game, export -> new game -> import restores the exact same page, French strings, and the real save left untouched; phone width has no overflow.
- Incident during testing (no lasting effect): a console `import()` of the session module after HMR created a second session that saved over the real save in the embedded browser; the original had been backed up first and was restored byte for byte. The rule is now in `instructions.md`.
- Open decisions: the Settings page is plain forms (the design pass will restyle it); whether language should also live only in Settings; a "Continue / Start over" prompt on first launch is not needed yet.
